# Design：邀请令兑换的局部 RLS 边界

## Context

见 proposal.md 的 Why。`AcceptInvite` 已有事务/保存点，邀请令为24字节随机值，库内只保存SHA-256。`TenantMiddleware` 在请求开始固定已有租户范围；`flow_invites` FORCE RLS 使尚未入会的受邀者无法发现目标邀请。已有 `withSystemContext` 可在同事务内暂时切换系统范围并恢复旧范围；`TenantTx` 会设置范围但不恢复嵌套调用者，因此不能直接用它包住兑换并返回。

## Goals / Non-Goals

**Goals:** 保留现有邀请令持有者兑换合同、登录校验和角色映射；在共享入口内完成可审计的最小凭证查询、目标范围写入与原范围恢复；保证单次兑换和失败原子回滚。

**Non-Goals:** 不改邮箱身份匹配规则、移除成员后重新入会语义或通用事务中间件；不新增安全定义函数、数据库策略、表结构或依赖，不把整个接受流程放进系统范围。

## Decisions

1. 继续使用 `AcceptInvite` 的现有事务/保存点，不改 handler 或前端。PG路径读取调用者原 `app.tenant_ids`，复用 `withSystemContext` **仅执行按精确 token_hash 定位唯一邀请并加行锁的一条查询**；不从客户端接收可信 tenant ID，不在系统范围枚举邀请或执行成员/账务写入。查询完恢复调用者范围。随机令牌本身是既有跨租户加入凭证，普通对象列表读取仍受原RLS限制。SQLite不执行PG上下文SQL，沿用现有事务行为。
2. 在已锁定记录上检查未使用、未撤销和有效期。只有匹配有效凭证后，才将当前局部范围设为该记录的精确 `TenantID`，条件领取邀请并创建该tenant/workspace的成员记录；所有写入保持目标租户范围，不清空到系统范围。最后恢复完整旧范围，不把新tenant意外留给调用方后续SQL。
3. 同令牌并发依靠行锁及现有条件更新，只有一次成功；无效令牌和终态邀请不产生成员或消费记录。所有数据库读、设置、更新、成员写和恢复失败必须返回并回滚该事务/保存点；不能把任意查询错误当“记录不存在”继续创建。保持原HTTP成功/无效邀请响应合同，不在错误响应中泄漏邀请详情或明文令牌。
4. 复用既有上下文能力可避免新增索引、RLS策略或SECURITY DEFINER函数；直接调用系统数据库连接会脱离当前事务/原子性，扩大请求全局范围会影响后续语句，均不采用。若最小PG检查证明上述局部方案不成立，先记录反证并调整工件，不先放宽策略。

## Risks / Trade-offs

- [系统上下文具有全租户可见性] → 严格限于令牌哈希单记录查询与行锁，回归检查无效令牌、范围恢复及独立其他租户不可见；它不是关闭ENABLE/FORCE RLS，仍需明确记录这条凭证查询例外。
- [嵌套保存点失败后设置泄漏或令牌被误消费] → 注入成员写失败，在调用事务内及事务外确认邀请仍未用、成员无残留、旧范围及旧查询可用；对成功与拒绝路径均核对原范围。
- [并发锁/条件领取返回旧值] → 两个普通连接竞争同一令牌，确认仅一成功，持久成员/工作区成员各一条，不发生重复兑换。
- [超出本次令牌兑换范围的角色或邀请问题] → 单独登记，保持本变更聚焦；没有新公开接口、迁移或新能力的计划。
- [源码检查不能证明已部署] → PG新测试库与18088既有数据隔离；本轮先交付源码RED/GREEN、相关专项和构建，运行镜像更新及真实API复验单独记录，未执行则明确待验。原测试账号和邀请不用于失败注入或破坏性探测。

## Migration Plan

无数据库迁移。已选 `codex/fix-invite-accept-rls-context`，hotfix直接执行默认设置，按用户要求实际先RED后GREEN，不启动子代理或自动代码审查。归档仍须本次最终确认；不推送/合并/发布。部署若需进行，必须保留原卷、使用现有隔离Compose附加配置并核对备份，不把旧镜像当当前源码。
