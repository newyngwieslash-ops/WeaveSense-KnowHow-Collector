# AC03 / AC04 后台发现与恢复工程证据

本页记录真实 Loom scheduler / coordinator 与迁移后磁盘 PGlite 的工程回归；B 站、抖音账号分页响应是自编固定夹具，不是实平台采集、真实账号授权或完整业务验收。

## 修复的真实缺口

- 每页 admitted jobs、分页记录、checkpoint 与 collection run 的 `items_new` 在同一事务提交。页 2 失败后，已提交页 1 的新增计数不再丢失；重复视频与后续窗口 overlap 不重复计入新增任务。
- 视频发现遇到事务结果不确定，先进入 `reconciliation_required`。磁盘重启后从持久页与游标对账，不能直接当失败后盲重做。末页已经提交但返回丢失时，使用持久的完成/边界标记结算，不重新请求第一页。
- 429 的正有限 `retry_after` 会约束任务重试与 source backoff（最多 86400 秒），同时保留原有指数退避；无效值不扩大授权或变成无限等待。
- 重试和对账从持久页恢复累计 item/page 消耗；请求的限制属于同一个 run，不能因重试重新获得完整额度。扫描 overlap 也占用限制，不能拿新增任务计数替代扫描数量。

## 可复跑检查

```bash
cd services/loom-engine
node --experimental-strip-types --test \
  flow/video-discovery-atomic.test.ts \
  flow/video-discovery-recovery.test.ts
```

八项自动检查已在本地通过：

1. 两个平台类型的账号各经历两个实际 scheduler 窗口；页 2 临时失败、关闭并重新打开同一路径数据库后恢复；得到 6 个唯一视频任务、4 个成功 collection run、2 个调度窗口。重放同一时钟不会再次创建窗口。
2. 页 2 返回 429；页 1 的新增数量与游标已提交、稳定水位未提前推进；重启后尊重 120 秒 Retry-After，达到边界后正确结算。
3. 中间页 COMMIT 已成功但返回丢失：先对账，再从已提交页 2 游标继续。
4. 末页 COMMIT 已成功但返回丢失：先对账，直接结算，不再调用外部分页接口。
5. COMMIT 前连接丢失、事务实际回滚：对账后安全重抓，未制造假任务或假 checkpoint。
6. 单页超过 item/page 上限、重复和乱序条目：跨三次调度与数据库重启恢复持久缓冲；不提前宣称完整覆盖，不丢任务、不重复计数。
7. 页 2 暂时失败后重试：累计 item 上限不重置，超出部分持久缓冲，不偷偷启动超限任务。
8. 达到 page 上限后丢失提交回包：重启对账只结算 partial，不重置 page 额度继续外部请求。

## 证据边界

这些测试不启动浏览器或聊天进程，证明 scheduler 不依赖前端存活；数据库确实关闭并从磁盘重开，但不是操作系统断电或远程 PostgreSQL 的网络分区试验。媒体下载、转录和模型结果没有在这两项测试文件中伪造完成，故不能据此声称新增知识候选或真实行业质量已验收。AC03 下游候选工程验证、实平台账号的两个新增窗口及业务评审须引用各自独立证据。原始 PRD / 任务台账未因这八项检查自动改为完成。
